What it is

sketchgen is a pipeline that takes a one-line creative prompt, expands it into a brief with testable assertions, generates a complete p5.js sketch in a single model call, gates the result in a headless browser, and publishes the survivors to a static gallery on GitHub Pages — with full provenance, paired human/agent judgments, and a self-prompting lineage that lets the gallery grow without human input.

It runs on one Oracle ARM node (16 OCPUs, 96 GB RAM), uses zero external dependencies beyond Python's standard library, and holds its entire state in a single SQLite file. The models — qwen3-coder:30b for execution and gemma4:e4b for vision judging and critique — are self-hosted via Ollama. No paid API key ever reaches the node.

The pipeline

PROMPT → PLAN (brief + assertions) → EXECUTE (single-shot sketch.js) → GATE (headless browser, assertions) → REPAIR (evidence-fed retries) → HOLD → PUBLISH
↑ idle: JUDGE (paired, blind) + CRITIQUE (→ child prompt) + SLEEP

One inference slot, one worker, one process. The worker fences the slot against interactive sessions (a second client causes 9× decode collapse), claims jobs from the queue, and when the queue is empty, does idle work — judging unpaired entries and critiquing published ones — before sleeping. Pause, stop, and resume are database rows, not signals.

The planner

Expands a short prompt into a prose brief (under 120 words) and a list of assertions drawn from a closed vocabulary: motion(idle), responds(click), responds(drag), responds(audio), uses(webgl), size(w,h), no_motion. The vocabulary is small by design — the planner cannot write an assertion the gate cannot execute.

The executor

qwen3-coder:30b-a3b-q4_K_M, single-shot. One prompt in (~2k tokens), one sketch.js out (~3k tokens), plus a statement the model writes about what it built. Not an agent loop — the first-day measurements showed an agent loop spends an hour on what single-shot does in a minute.

The gate

Playwright + headless Chromium, deterministic (seeded random, frozen clock). Fixed checks on every job: console errors, frame advancing, sound library state. Then the planner's per-job assertions. A preflight scan catches the most common crash class — a variable that shadows a p5 global (let line hiding line()) — and puts the explanation above the evidence before the executor sees it. On failure, the gate's evidence (not a verdict) goes back for bounded repair. On success, the entry is held for human review.

Publication

Held entries are published or rejected by a human. Publication pushes to GitHub Pages with a write-only deploy key — the entry directory, the commit with the executor's model as Co-Authored-By, and the index re-rendered behind it. Files are scanned for email addresses before anything touches the public repo.

The hypothesis

The research idea is not "can AI make art." It is: when humans and agents judge the same artefacts on the same questions under blind conditions, how much do they disagree?

The two questions

1. Which is closer to its brief?
Fidelity — how much of the brief is on the canvas.

2. Which would you rather look at?
Taste — there is no correct answer.

Two populations, never one aggregate

Humans and agents get identical frame strips, identical briefs, identical questions. A Bradley–Terry fit gives every entry a score per population. The divergence between the two is the measurement. Nothing in the system ever collapses them into one number.

Blinding

The agent judge never sees: a human vote, a Bradley–Terry score, an engagement tally, the producing model, the submitter, or the rules file. judge.py:assert_blind() enforces a banned-field list against the rendered prompt before anything is sent. The human sees the agent's verdict only after their own choice — compatible with "never hidden," incompatible with anchoring.

The A/B experiment

Every job records its rules file — treatment carries structured p5.js conventions (the library trap, global mode, canvas sizing, verification norms) while control carries the class repo's generic context. The gallery's own paired comparisons score the difference, making sketchgen an A/B rig measuring whether structured context improves creative output from the same model on the same prompts.

The self-generating loop

When the queue empties, the worker critiques published entries using the local vision model. The critic writes one sentence — under forty words, no code — describing a visible change for the same sketch made again. That sentence becomes the child's prompt:

entry 2: "a breathing grid of squares"
└─ CRITIQUE → "the same grid, and this time the pulse colors are randomized upon impact"
└─ entry 9 (generation 1)
└─ CRITIQUE → …
└─ entry N (generation 2) — line continues to depth 3, then waits for a human

Lineage runs three generations unattended; at depth 3 the child is created but held for human review before the line can extend further. Every entry stores its parent, its generation, the critique, and the critic's model id. The provenance graph — which prompt begat which, through which model, past which gate — is what "generates itself" means.

What the gallery shows

  • Bradley–Terry scores per population per question, rendered as percentile bars on each card
  • An entry-page compass: rather look at it across, closer to its brief up, a dot for humans and a ring for agents, the line between them the gap
  • Human and agent populations that sometimes agree and sometimes diverge — the first real points toward MEASURE[agent-human-correlation]
  • Multi-generation lineage trees: prompts evolving through self-critique
  • A rejection record with kept failures — "a gallery that only shows successes is not a record of anything"
  • Full provenance on every entry: tokens, wall time, attempts, seed, model ids, prompt versions, node shape, Co-Authored-By the executor model

Architecture

On the node

Worker — systemd user service, one job at a time, slot-fenced
Ollama — qwen3-coder:30b (executor), gemma4:e4b (judge/critic)
Gate — Playwright + headless Chromium
Web UI — stdlib http.server on 127.0.0.1:8081, SSH tunnel only
Sync — 5-min timer pulling from the write path
Database — one SQLite file, 9 tables + critiques

Off the node

Gallery — GitHub Pages, static HTML, pushed by deploy key
Write path — Cloudflare Worker + KV, GitHub OAuth (username only)
Compare — paired judgment UI, humans vote before seeing agent scores
Engagement — views and likes, kept apart from judgment by design

The database

12 tables across 5 migrations, all in WAL mode. jobs and their attempts, the entries the gallery shows, paired judgments, lineage, critiques, engagement and likes, sync_state for the write-path watermark, meta for the worker's own timestamps, and a singleton control row. A job's legal moves are enforced in db.py (TRANSITIONS), not in SQL.

The operator UI

Five screens over SSH tunnel (stdlib http.server, 3,100 lines): Console (node vitals, five-segment load meter, tokens-per-5-minute sparkline, production funnel), Queue, New Job, Job Detail (live SSE transcript), and Held (publish/reject). Every screen carries the worker-state pill and pause/stop/resume controls. No framework, no JS build — server-rendered HTML with a two-second poll. Navigation items carry live summaries: an amber superscript for held entries, a green/red count for queue state, a decode rate on the tokens gauge.

The codebase

~14,600 lines of application Python, ~8,600 lines of test (14 files, stdlib unittest), ~1,200 lines of gallery CSS/JS, ~560 lines of Cloudflare Worker. 108 commits, 49 PRs, built between 2026-09-13 22:07 and 2026-09-14 14:35 EDT. What it demonstrates

Self-hosted AI can produce at scale. Close to 100 high-quality creative sketches in under 24 hours, on commodity hardware, with open-weights models, zero paid API calls, and full provenance — every token counted, every decision recorded, every model named.

The tooling is the multiplier. The gate, the preflight, the evidence-fed repair loop, the single-shot execution model, the closed assertion vocabulary — each is a design decision that compounds: the gate catches what the model can't see, the preflight explains what the gate caught, and the repair loop gives the model another chance with that explanation. Without them the same model produces the same code and gets stuck on the same bugs.

The interesting question is the disagreement. Not whether agents or humans are right, but where they diverge on taste and fidelity — and whether that divergence is a function of the artefact, the context the model was given, or the population doing the judging. That question can only be asked with blind conditions, paired comparisons, and separate scores.
